# 2026-09-15 BWG CPA 真实客户端 key 公网生成验收

用户授权在保留公网 Nginx、随机 capability path 和单一客户端 key 的前提下，
从当前 Windows 工作站执行真实公网生成验收。本次只触发 `bwg`，不连接或修改
`zz`，不执行持续压力流量。

## 方法

- 通过一次受控的 BWG 读取在内存中取得当前客户端 key、随机路径和 server name；
  不写入文件、不输出命令行、不记录 key 或路径。
- 从工作站访问 `https://<server>:8443/<random>/v1`，先用真实 key 请求目录，
  再按认证目录中实际暴露的路由各发送一次短 `chat/completions` 请求；请求间隔
  2 秒，`max_tokens=16`，提示内容和响应正文均不写入证据。
- 遇到上游失败不自动重试，避免把验收变成重放或放大流量。

## 结果

| 检查 | 结果 |
| --- | --- |
| 真实客户端 key 公网目录 | HTTP 200，目录 14 个模型 |
| `gpt-5.6-luna` / OAuth | HTTP 200，返回模型正确，`finish_reason=stop`，耗时约 1.64s |
| `r1/gpt-5.6-luna` | HTTP 408，未重试，属于当前 r1 上游不可用/超时信号 |
| `glm-5.3-flash` / zhipu-plan | HTTP 200，返回模型正确，但 `finish_reason=length`；短上限下未完成，不判定为完整质量通过 |
| `r2/*`、`deepseek-*` | 当前认证目录未暴露，未强行调用 |

## 结果解释与复验

- 这轮证明了真实客户端 key、公网 TLS/Nginx 随机路径、认证和三条当前暴露路由
  的实际请求链路；不是本机 loopback 假探针。
- Apply 后 strict doctor 仍为 `DOCTOR_CONTRACT_OK`；有效路径无认证 401，裸路径和
  错误路径 404，CPA 仍为 127.0.0.1:8317，Nginx 仍为公网 8443。
- 请求后的 access-log 汇总为：入口限流标记未触发（仅 `PASSED/PASSED` 或非限流位置），
  本轮新增 1 个 408；因此 r1 的结果不能归因于 Nginx 限流。
- 没有执行持续流量或并发压测：对单一客户端 key 和上游 OAuth/计划账号，持续压测本身
  会增加 429、冷却、封禁和计费风险，不能作为防封号验收手段。

## 未闭合边界

- r1 上游需要供应商侧可用性/权限核查；本仓不自动重试或跨供应商改路由。
- GLM 返回 200 但本次短 token 上限下未完成；需要在用户认可成本与配额后，另行做一次
  单次较大上限的质量验收，不能把 200 等同于内容完成。
- r2/DeepSeek 要先恢复并确认其 provider credential/模型暴露，再做单次验收；本次不
  通过强行请求不存在的公开模型制造无意义失败。

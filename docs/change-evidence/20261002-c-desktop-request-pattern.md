# C 只读排查：desktop 会话的请求模式与「4 会话 429」的完整因果

日期：2026-10-02。执行窗口：02:27–02:35 UTC。方法：**全程只读**（journalctl + access.log + 配置读取）。

## 结论：desktop 请求是**串行**的，「4 个会话」不是并发放大的来源

**真正机制：请求耗时太长（排队 30–93s + 上游 30–95s），导致 in-flight 累积超过 lane 的 6 槽。**

即：**症状 C（慢）与症状 B（429）是同一个病，不是两个病。**

## 证据链

### 1. `client_request_hash` 的语义（源码确认）

`cpa-admission.py:706`：
```python
client_request_hash = diagnostic_hash(
    self.headers.get("X-Client-Request-Id") or self.headers.get("X-Request-Id")
)
# diagnostic_hash = sha256(value)[:12]
```

⇒ 它是 **desktop 会话/任务 ID**。同一 hash 出现多次 = **同一会话的连续多个请求**。

### 2. 单会话严格串行（决定性证据）

近 30 分钟，6 个活跃会话的请求节奏：

| 会话 hash | 请求数 | 每秒最多 | 突发秒数 | 间隔 min / median / max |
|---|---|---|---|---|
| `d585cda804c2` | 66 | **1** | **0** | 3.0 / 19.0 / 103.0 s |
| `7477b3542fe6` | 55 | **1** | **0** | 4.0 / 15.0 / 106.0 s |
| `8b29df53d892` | 38 | **1** | **0** | 1.0 / 25.0 / 411.0 s |

- **`max_per_sec = 1`、`burst_seconds = 0`** ⇒ 任何会话都**从不在一秒内发两个请求**。
- 全局每秒请求数峰值也**只有 ×2**。

⇒ **desktop 不存在"单会话并行发请求"的放大**。（方向 2 的假设被否定。）

### 3. in-flight 长期高于 lane 容量（真正的 429 成因）

- **常态 in-flight = 6–16**，而 **`chatgpt-oauth` lane 容量只有 6**。

### 4. 因果链（定案）

```
desktop 发请求（串行，间隔 15–25s）
   ↓
该请求在 admission 排队 30–93s（lane 只有 2 个 inflight 槽，其余排队）
   ↓
上游再耗 30–95s（OAuth 账号吞吐慢，见症状 C）
   ↓
单请求占用 60–190s
   ↓
6 个会话以 15–25s 间隔发下一轮 ⇒ in-flight 累积到 6–16 > lane 容量 6
   ↓
第 7 条起 reason=busy 秒拒（retry_after=10）
   ↓
客户端看到 "exceeded retry limit, last status: 429"
```

**核心**：不是"并发太多"，是**每个请求太慢**，慢到让串行的 6 个会话也把 6 槽占满。

## 对三个方向的裁决

| 方向 | 裁决 | 理由 |
|---|---|---|
| **2. 查 desktop 并行** | ❌ **否定** | 实测单会话 `max_per_sec=1`、`burst=0`，**不存在客户端并行放大**。不是修复点。 |
| **1. 加 lane 容量** | ⚠️ **有效但治标** | in-flight 常态 6–16，把 lane 提到 8–16 能立即减少 `busy`。但在上游只有 2 路真实吞吐的前提下，加容量只是把 6 个请求从"被拒"变成"排队更久"——**总完成时间不变甚至更差**。 |
| **3. 对齐 nginx 预算** | ✅ 已做（12） | 无害。但与本 429 无关（nginx 层 N≤13 零拒绝）。 |

## 真正的根因与唯一有效方向

**根因 = 上游 OAuth 账号吞吐不足**（单请求 30–95s，`plan_type: plus` 300min 窗口）。

- 加 lane 容量治标：让更多请求**排队**而不是被拒，但**不提高总吞吐**。
- 唯一治本：**提高上游账号容量**（升级 plan / 增加账号数 / 分流到其他 lane）。
- 次要缓解：**降低单会话的请求频率**（如果 desktop 有"少发中间轮"的选项）。

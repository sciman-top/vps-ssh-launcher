# C 只读排查：Desktop 请求模式与「4 会话 429」的证据边界

日期：2026-10-02。执行窗口：02:27–02:35 UTC。方法：**全程只读**（journalctl + access.log + 配置读取）。

## 复核结论：现有统计不能证明 Desktop 请求严格串行

2026-10-02 源码复核撤回原文的“严格串行”“完整因果”与“唯一有效方向”结论。下列历史统计保留用于说明采样结果；请求身份、重叠区间和窗口口径未闭合的部分不能作为定案依据。

已确认 admission 记录排队时长，慢请求可能增加连接占用。具体 429 仍需逐条区分 Nginx 限流、lane busy、lane cooldown 和上游错误，不能仅凭请求间隔归为同一个原因。

## 证据链

### 1. `client_request_hash` 的语义（源码确认）

`cpa-admission.py:706`：
```python
client_request_hash = diagnostic_hash(
    self.headers.get("X-Client-Request-Id") or self.headers.get("X-Request-Id")
)
# diagnostic_hash = sha256(value)[:12]
```

源码只证明它是请求头值的关联哈希。请求头是否稳定代表 Desktop 会话/任务 ID，仍需客户端发送端证据；同一哈希出现多次不能单独证明同一会话、请求类型或重试关系。

### 2. 按请求头哈希分组的启动频率（不足以判断串行）

原采样报告称近 30 分钟有 6 个活跃分组，下表列出其中 3 个。此处“会话 hash”沿用原表标签，实际身份尚未证明：

|---|---|---|---|---|
| `d585cda804c2` | 66 | **1** | **0** | 3.0 / 19.0 / 103.0 s |

- `max_per_sec = 1`、`burst_seconds = 0` 只说明该采样分组没有同秒启动多条请求；间隔超过一秒的请求仍可能重叠。

判断串行必须按同一请求 ID 配对开始、结束或断连事件，验证后一条请求开始时间是否晚于前一条结束时间，并核实会话身份和辅助请求类型。现有统计尚未完成这些步骤。

### 4. 可成立的机制与尚未证明的环节

`waited_ms` 在 lane acquire 阶段计算，仅包含 admission 等待；`upstream_result` 在上游响应处理结束时记录。结束时间减排队时长会漏掉上游处理时间，不能恢复请求开始时间或完整连接占用区间。

原因链同时假定“6 个会话严格串行”与“这 6 个会话产生 6–16 条同时在途请求”，两者缺少辅助请求、重试或其他客户端来源的解释。必须重新配对请求事件后才能判断。

lane 的 `max_inflight = 2` 与 `max_pending = 4` 分别限制上游执行和等待队列，两者之和为 6 条保留请求。Nginx 连接计数还可能包含其他 lane、辅助请求和其他客户端，不能直接等同于某一 lane 的 inflight。

## 当前可支持的结论与后续判据

后续受控探针已捕获 OAuth 上游 `usage_limit_reached` 和有效 Retry-After，admission 进入 cooldown；这是对应请求失败的直接证据。上游延迟与这些配额错误可以同时存在，不能由本报告证明所有历史 429、容量提示和慢请求都只有一个原因。

- 对配额 cooldown，应尊重上游 Retry-After，在到期后用受控请求检查恢复；到期不保证上游配额已经恢复。
- 账号容量与其他 lane 分流属于可评估选项，不能直接宣称升级 plan 是唯一有效修复，也不能据此静默切换用户默认模型。
- 对 busy 和慢请求，按同窗口请求 ID、lane、状态、开始/结束时间和排队时长分析；只在证据支持时调整预算。

## 证据边界

- 全程只读，未改任何配置。
- 旧重建不能可靠反映完整连接占用，也不能推出连接占用与 lane inflight 的差值就是排队量。
- 原报告称剔除了 02:19–02:26 压测时段；不同表格是否使用相同排除条件尚未闭合。
- admission journal 的外层记录是 JSON，`MESSAGE` 是文本事件；将 `MESSAGE` 当 JSON 解析后的空结果不能证明事件不存在。
- 未宣称 `natural_live_accepted`。

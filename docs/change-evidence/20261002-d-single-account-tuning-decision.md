# D 决策分析：单 OAuth 账号约束下的参数优化评估

日期：2026-10-02。窗口：02:32–02:42 UTC。前提：**操作者只有 1 个 ChatGPT OAuth 账号**。
方法：只读采集 journalctl + access.log + 源码常量审查 + Little 定律定量推算。

## 结论：**没有值得执行的参数修改。当前配置已是单账号约束下的最优。**

三个候选动作全部**净负收益**，故不改。

## 实测基线（2 小时，`chatgpt-oauth` lane）

| 指标 | 值 |
|---|---|
| 事件总数 | 492（483 配对成功） |
| 成功 | 475 |
| 拒绝 | **17（3.5%）** —— `busy` 16、`downstream_gone` 1 |
| 排队（`waited_ms`） | p50 **10.1s** / p90 34.7s / max **93.4s** |

| 排队 | 316 / 483（**65%**） |
| 真实吞吐 | 01:00 = 4.58/min；02:00 = 3.33/min |

## 三个候选动作的定量评估

### A. `max_inflight` 2 → 3 ❌ 不做

- 槽位 6→7，上游并发 2→3。
- **风险不对称**：唯一账号 `plan_type: plus`，单请求实测 30–95s。
  加并发极可能触发容量失败（`usage_limit_reached` / `server_is_overloaded`），
  一旦触发 → **整条 lane 冷却 60s 起（`cooldown_schedule_seconds` 首档）**，
  比当前 3.5% 的零星 `busy` 严重得多。
- 收益不可证（上游真实并发能力未知），风险可证。
- ⇒ **拒绝。**

### B. `max_pending` 4 → 8 ❌ 不做

- 槽位 6→10，可消除大部分 `busy`。
- **Little 定律代价**（L = 槽位, λ = 到达率 0.06 req/s）：
  - 旧：W = 6 / 0.06 = **109s**
  - 新：W = 10 / 0.06 = **182s**
- **反噬**：`queue_timeout_seconds = 120` 是硬编码常量。等待推到 182s 均值后，
  **大量请求会从「被 busy 秒拒」变成「排到 120s 超时被拒」**，
  拒绝率可能不降反升，且被拒者还白等 2 分钟。
- ⇒ **拒绝。**

### C. `queue_timeout_seconds` 120 → 更大 ❌ 不做

- 放宽超时能让慢请求排进去，但**不提高上游吞吐**，只是把队列积压时间拉长。
- 且它是硬编码常量（`ADMISSION_QUEUE_TIMEOUT_SECONDS = 120`），
  改动需同改 `cpa-admission.py` + `.json` + 测试 + runbook，**收益不抵变更成本**。
- ⇒ **拒绝。**

## 为什么"不改"是正确的

1. **症状本质是上游吞吐不足**（单账号，3.3–4.6 req/min），本地任何参数都在分配稀缺资源，
   不能创造资源。3.5% 的拒绝率是**削峰的正常代价**，不是故障。
2. **当前参数已把资源分配合适**：
   - 65% 的人排队等（p50 仅 10s，可接受）；
   - 只有 3.5% 在峰值被拒（客户端重试即可）；
   - 上游并发锁在 2，**保护了唯一账号不被打爆**。
3. **加大队列/并发都是把风险从"少量拒绝"转移到"大量长等待"或"整条 lane 冷却"**，
   对不同用户的体感是**变差**。

## 硬件/配置层已无可优化项（全部已验证）

| 层 | 状态 | 证据 |
|---|---|---|
| nginx 连接预算 | ✅ 20（> lane 容量） | 远端 `limit_conn cpa_cc 20`，doctor OK |
| nginx 速率限制 | ✅ `rate=10r/s burst=10` | 不与当前流量冲突 |
| admission 半开队列 | ✅ 已修（`1ffcd45`） | 无 `half_open_probe` 拒绝 |
| admission Retry-After | ✅ 已修（`d35d24f`/`d711c1d`） | `retry_after_classes` 仅 `absent` |

| 本机 `request-retry` | ✅ 强制 0（v1.3.65 补丁） | 无重试放大 |
| lane 容量 6 | ✅ **经本报告论证为合理值** | 见上 |

## 唯一剩余方向（需外部资源，非本地可解）

- 增加上游账号（多 OAuth 账号 → 多 lane / 提高 `max_inflight` 才有意义）。
- 或在客户端**降低请求频率/缩短会话轮次**（减少 λ）。

## 证据边界

- 全程只读，未改任何配置。
- Little 定律推算假设稳态泊松到达，实际到达有突发，故为量级估计而非精确预测。
- 未宣称 `natural_live_accepted`。

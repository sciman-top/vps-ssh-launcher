# BWG CPA v8.0.48 host canary（2026-10-30）

## 目标与边界

用户授权在 `bwg` 单机上升级 CLIProxyAPI 到官方 `v8.0.48`，保留现有 OAuth 账号、CN/INTL realm、准入与回滚护栏，并授权必要时修复本项目代码。WorkBuddy 上游最新为 `v0.8.91`（2026-10-30 发布）；workbuddy 源码 delta 仅为 auth.parse operator-field whitelist 修复（本仓不经面板编辑 auth，无实效）加纯测试提交，registry version `0.9.81→0.9.82`，因此插件保持现役 0.9.81 构建不变（与 v8.0.46→v8.0.47 轮同判例）。

本轮没有账号/IP/设备轮换、冷却清除、重试或并发提升，也没有发送新的 OAuth 生成探针。缓存与流式验收只使用非 OAuth 的 `glm-5.3-flash` 路径。

## Fixture harness 修复（项目代码）

首轮 accept 暴露两类与 v8.0.48 无关的既有缺陷，均已修复在源（`scripts/remote/`）并经 `tests/test_cpa_updater_apply.py` 全绿：

1. **lane-hold 读穿宿主**：fixture 的 updater 环境未覆盖 `LANE_HOLD_STATE_DIR`，`cpa-auto-update.sh` 回落读宿主 `/var/lib/cpa-admission`；生产 workbuddy 活跃流量的 write-ahead `unverified_request` 标记（inflight 期间设计内瞬态）恰好落在 success 场景窗口即非确定失败。修复：`cpa-update-acceptance.py` 的 `updater_env` 钉定 `ROOT/state/admission`，`cpa-acceptance.py` 预置三个 lane 的空 risk 文件（claude 墓碑按 deploy 侧契约保持缺席）。
2. **复用 `$V` 的场景残留**（第二轮暴露）：上一次运行的 `upstream-mode=ok` 使 overload 场景静默变成成功流；上一次 UNVERIFIED 退出按契约留下的 `cpa-update.pending` 使 start_fail 场景撞 pending 门。修复：场景序列开始前分别清理（`upstream-mode` unlink、`PENDING_PATH.unlink(missing_ok=True)`）。
3. overload 诊断字段 `body_head` 保留（一次性行为证据：v8.0.48 将 200 流内 `response.failed` 以 `event: error` SSE 形态中继且保留 `server_is_overloaded` 标记，分类行为未变）。

## ChatGPT desktop SSE idle timeout + 429 归因（只读诊断，真实远端）

症状：ChatGPT desktop 用公共 key 时反复 `stream disconnected before completion:
idle timeout waiting for SSE`，并偶发 `exceeded retry limit, last status: 429`。

### 根因（两个独立问题，均已实测定位）

1. **idle timeout = 部署侧 admission 缺少 SSE 保活与分帧**。
   - 链路：client → nginx 8443（`proxy_read_timeout 300s`）→ **8318 admission 前置代理**
     → CPA 8317。admission 是 2026-09-26 引入的**新中间层**，它对每个响应做了
     `for key,value in response.getheaders(): send_header(...)` 但**丢弃 HOP_BY_HOP_HEADERS**，
     其中含 `Transfer-Encoding`；上游 chunked SSE 到下游就变成"无 TE、无 CL、靠连接关闭定界"。
   - 旧版还显式发 `Connection: close` 给上游，`http.client` 一旦收到 close 应答就把
     `sock` 置 None → **无法对上游 socket 做读超时拉伸**，读默认 300s。
   - 无心跳：上游事件间隔 >300s（长思考/长工具调用）时，nginx 对着 8318 的
     `proxy_read_timeout 300s` 先超时断流，客户端报 idle timeout。

## admission SSE 保活修复：残留致命缺陷（断连期 lane 租约永久泄漏）

修复方向已被并行会话改为「专职 `_read_sse` 读线程 + `queue.Queue`，
主循环 `queue.get(timeout=heartbeat_interval)` 作为可中断等待」（取代原
`select()` 方案）。**`select()` on `conn.sock` 不可用**：`BufferedReader`
预读后数据在其内部缓冲，裸 socket 不再可读，`select` 恒 False（本地实测：
`read1#1` 后 `fp.peek()`=`b'\r\n'` 但 `select(raw sock)`=False）。

**残留缺陷（高severity，本地复现 3/3 稳定）**：客户端在 SSE 流中途 RST 时，
`_proxy` 的 `finally` 里 `conn.close()`（`http.client` line 1027→435→`_close_conn`）
**永久阻塞**，因为 `_read_sse` 线程仍 park 在同一 `HTTPResponse.fp` 的
阻塞 `recv()` 中；`close()` 要拿 reader 的锁，拿不到。→ 外层的
`lanes[lane].release()` 永不执行 → `inflight` 恒 1，lane 槽位泄漏、
连接处理线程泄漏。

栈证据（`outputs/dbg18.txt`）：
```
t=1.0  Thread-3 _proxy:592 -> join(1094)          ; Thread-6 _read_sse readinto:719
t=2.0  Thread-3 _proxy:636 -> close -> _close_conn ; Thread-6 仍 readinto:719
t=3.5  同上，inflight=1
```

**Windows socket 语义（本次多轮实验定论）**：
- `shutdown(SHUT_RDWR)` **不能**唤醒另一线程 park 的 `recv()`（`dbg21`:
  `sock.close()` 同样不能，`reader woken=False in 3.0s`）。
- `HTTPResponse.fp.close()` 与并发 `read1()` 在同一 `BufferedReader` 上串行；
  `conn.sock=None` 也救不了（`dbg19`: `conn.close()` 仍耗时 29.5s，直到上游关闭）。
- `settimeout` 会永久毒化 `SocketIO._timeout_occurred`，不可用于分片等待。

**修复方向（已本地验证有效，未写入仓库）**：
1. **`lease.release()` 必须移到 `conn.close()` 之前**（当前顺序相反，
   `cpa-admission.py:634-640`）。**仅此一步即可消除 inflight 泄漏**：
   冻结副本上实测「先 release + 守护线程 close」→ 断连场景 **6/6 released**
   （修复前 0/6），且 SSE 正常完成路径不回归（1.5s / 2 帧 / 4 keepalive）。
   证据 `outputs/dbg2-fixed.txt`、`outputs/dbg8-fixed.txt`。
2. 连接回收不得与 reader 线程争锁：`conn.close()` 前要么确认 reader 已退出
   （`sse_reader.join()` 无超时→但 Windows 上可能永不退出），要么把
   `conn`/`resp` 的关闭交给 reader 线程自身（读线程退出时自然释放），
   主线程只做 `lease.release()`；或用守护线程 `conn.close()`（实测可行）。
3. 不要依赖 `shutdown()` 作为「唤醒」手段——`_release_upstream()` 的注释
   声称的 nudge 行为在 Windows 上不成立。

完整交接文档：`outputs/admission-sse-lease-leak-finding.md`。

## 断连释放失败的**确切机制**（最终定位，HEAD=`90f72a5`）

插桩副本逐行时序（`/tmp/fz4-run4.txt`）证明主循环有两条路径：

```
loop top client_lost=False
buffered=True                ← peek() 假阳性
calling read1
read1 returned 11
loop top client_lost=False
loop exit                    ← 通过（1.47s）
```

- **通过**：`_buffered_upstream_data()=False` → `select(0.3s)` 超时 →
  `continue` → 回到 `if client_lost.is_set()` → `break`。
- **死锁**：`_buffered_upstream_data()` 返回 **True**（`BufferedReader.peek()`
  对 chunked 流**假阳性**）→ 跳过 `select` → 直接 `response.read1()` →
  **永久 park 在 `recv()`**（静默上游；Windows 下 `shutdown()` 不能唤醒）→
  永远回不到 `client_lost` 检查点 → **租约 + 线程双泄漏**。

**波动性来源**：是否阻塞取决于检查瞬间 `peek()` 是否看到缓冲字节。
同字节代码（`e7a368c6`）在仓库与副本表现相反；**加一条 `logging.warning`
即可翻转结果**。`dbg23`：`hb=0.3→未释放 / 1.0→0.05s / 3.0→未释放`。

**结论**：`_buffered_upstream_data()`（peek 判就绪）是**净负收益**——
它避免「裸 socket 看似空闲但缓冲有数据」的假阴性，却引入「缓冲看似有数据但
`read1` 仍会阻塞」的**假阳性**，而假阳性代价是永久死锁。
正确方案是**专用读线程 + 队列**（读线程独占阻塞读，主线程只
`queue.get(timeout=...)`，超时可中断、可复检 `client_lost`），
分支判据用 `sse_queue is not None`（**不要**叠加 `upstream_sock is not None`）。
完整方案见 `outputs/admission-sse-lease-leak-finding.md` §3。


## 落地：读线程 + 队列方案 + 新发现的 `response.close()` 阻塞点（本地已提交前）

**背景**：并行会话的 `8f3004a`（HTTP/1.0 上游）只删了块级预读，**没有删
`peek()` 就绪门与主线程 `read1()`**。断连期仍会 park。本会话按上文 §3 方案
把 admission 转发循环改为**专用读线程 + 队列**。

### 远程只读实测（先做，再改代码）

用 `connect.ps1 -Command` 向 CPA `127.0.0.1:8317` 发 HTTP/1.0 流式请求
（客户端 key 从远端 `config.yaml['api-keys'][0]` 读取，不落盘）：

```

chunked: no
eof_received: True          # 完整流以 EOF 正常终止
has_completed_event: True   # 含 response.completed
total_bytes: 7996 / elapsed 9.37s
```

**结论**：CPA 对 HTTP/1.0 请求**不分块**，`8f3004a` 的 HTTP/1.0 前提在生产
成立；`dbg25`（上游返回 chunked 时断连不释放）**当前不可达**，属理论边界。

### 本地改动（`scripts/remote/cpa-admission.py`）

1. **删除 `_buffered_upstream_data()`（peek 就绪门）整个函数** —— 假阳性死锁源。
2. **SSE 路径改读线程 + 队列**：`_read_upstream(sink)` 独占全部阻塞
   `response.read1()`；主循环只 `queue.get(timeout=heartbeat_interval)`，
   超时 `continue` 回顶部复检 `client_lost`/`_client_gone()`。
   **结构性保证**：主线程永不在读上游时 park，断连后**最迟一个心跳切片**
   释放租约（生产 15s）。非 SSE 分支保持单次 `read1()` 循环。
3. **`_retire_reader(reader, proxy)`**：读线程可能 park 在已交给 response 的
   单次连接 socket 上，Windows 无 API 可唤醒 → 放弃该线程是安全的
   （连接单次使用、随请求销毁，无跨请求数据丢失）。
4. **新发现（关键，插桩定案）**：`finally` 里 `conn.close()` **不阻塞**，
   真正阻塞的是紧随其后的 **`response.close()`**（`fp.close()` 与仍在
   `read1()` 中的读线程争同一 `BufferedReader` 锁 → 永久 park）。
   实测：`dbg-leak2` 顺序打出 `finally enter → after conn.close →` 然后**卡死**。
   → 修法：`response.close()` 放进守护线程 `join(timeout=2)`，
   **租约释放无条件紧随其后**。这才是断连用例失败的根因。
5. `/healthz` 增 `retired_readers` 计数，`_retire_reader` 打
   `retired_upstream_reader resident=N` warning —— 回归可观测而非静默堆积。

## Phase 3：429 真根因 = 熔断阈值过敏感（提交 4f9e541，已投影）

**用户反馈「还是频繁报 429」** —— Phase 2 容量放宽（3/4/120）没解决。

**重新定位（这次读了 CPA 容器日志，之前只看 nginx）**：

6h 窗口 lane `chatgpt-oauth`：
| 上游 200 | 53 |
| capacity=true | **2**（均瞬时 503）|
| reject cooldown | 9 |
| reject half_open_probe | 5 |

**2 次故障 → 14 次拒绝，放大 7:1。**

容器日志（`cli-proxy-api`，注意不是 `cliproxyapi`）：
```
18:55:09 503 13.5s err={"code":"server_is_overloaded",
                        "headers":{"x-retry-metadata":"NO_MORE_RETRY"}}
18:55:21 200 25.6s   ← 12 秒后恢复
```
provider 瞬时过载、12 秒恢复，而阈值=1 让熔断器锁死 lane 整个 60s 首档
→ 该分钟 desktop 每次重试都吃 429 → "持续 429 风暴"。上游从未真故障。

**我上一轮的推理错在哪**：我写"容量修好后原触发条件消失，故无需阈值保护"
—— 错。触发条件不是容量，是**上游偶发过载**，与容量无关。容量修复本身
仍是有效的（并发能力确实是瓶颈之一），但它不是 429 的原因。

**改动**：
1. `ADMISSION_COOLDOWN_FAILURE_THRESHOLD = 2`（连续 2 次才熔断；
   上游给 Retry-After 仍立即熔断）。
2. **普通成功请求也清零 `failure_streak`** —— 原代码只在半开探测成功时清零，
   所以计数是非连续累加。这是我新写的测试
   `test_lane_resets_the_failure_streak_after_a_success` 抓出来的真实缺陷。
3. 60s 首档保留；容量 3/4/120 不动。

**投影**：只读 doctor 仅 `cpa-admission.py` MISMATCH →
`-Apply` 9/9 VERIFIED + `READY_STATUS=200`
（备份 `…T141048.282865334Z`）→ doctor `DOCTOR_CONTRACT_OK`（9/9 MATCH）。
**回读远端**（吸取上轮教训）：阈值常量在位、`sha256=e93ddba5…` 与本地 HEAD
blob 一致、新 PID 100895 @14:10:52 UTC。

**验收**：双轮 ×2 并发 = 4/4 `200/7436B/completed=True`；
新进程 `capacity_true=0`、`cooldown_rej=0`、`halfopen_rej=0`、`busy_rej=0`、
`lane_reject=0`、journal 0 error。**放大比 7:1 → 0:0**。
公网 responses 429：重启前 36、重启后 0。

**边界**：验收仍是 urllib 模拟，且重启后公网无新 responses 流量；
最终以用户实际 desktop 会话为准。

**方法论教训**：诊断 429 必须读 **CPA 容器日志**（provider 原始错误），
不能只读 nginx access log —— nginx 的 `upstream_status=429` 包含了
**admission 自己的 429**（对 nginx 而言 8318 就是 upstream），
`bytes=203` + `Server: BaseHTTP/0.6 Python/3.12.3` 就是 admission 拒绝体。
我前两轮把 203 字节读成"真上游 429 响应"，结论侥幸对、论据是错的。

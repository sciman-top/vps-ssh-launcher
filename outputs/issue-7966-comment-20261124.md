# Upstream comment draft for CLIProxyAPI#7966 (to post via gh)

Confirmed on a clean v8.1.2 (85225381) build: the same four failures
(`TestIssue6825StreamToolIndicesAcrossChunks`, `TestIssue6825ToolPolicyKeepsHistoricalSignature`,
`TestIssue6825PayloadRulesRemainFinal`, and the interrupted-message pairing
test). We traced both regressions one level deeper than the test failures and
have a reconciling fix running in production. Sharing the analysis in case it
helps:

## 1. `4df055de` fragments the dominant real-world shape

The emitter treats every functionCall start as a streaming start: it emits an
unclosed `{...` fragment per call and appends the closing braces at terminal.
But the dominant Antigravity shape is *complete* calls — each part carries a
full functionCall (name + complete args), including parallel calls grouped in
one chunk. On that shape the current code produces six deltas for three calls:
indices `[0,1,2,0,1,2]` with arguments split as
`{"tz":"UTC"` / `{"tz":"America/Santiago"` / `{"tz":"Asia/Tokyo"` / `}` / `}` / `}`.
Clients that assert "a new index must equal len(calls)" fail outright, and
clients that concatenate argument deltas in stream order get invalid JSON.

## 2. `ae88b00c` reorders interruption turns

The unconditional deferral places a pure-user turn that arrives *before any
response of the pending group* after the grouped responses. For an
interruption (user cancels a tool loop and sends a new instruction before
responses arrive) that inverts chronological order — which is what the
interrupted-message pairing test asserts against.

## 3. The two commits' test contracts are mutually exclusive on unmarked streams

`ContinuesUnnamedFunctionCallAtActiveIndex` / `UsesUpstreamIDForUnnamedContinuation`
require fragment deltas; `TestIssue6825*` requires one complete delta per call.
No single emission strategy passes both unless something distinguishes a
*streaming* start from a *complete* call. The protocol already has that
dimension: `willContinue` and Vertex-style `partialArgs`.

## Reconciling fix (running in production here)

Response side (chat-completions stream):
- a start buffers its argument members; if it is **not** marked
  (`willContinue` / `partialArgs` absent) it is emitted immediately as ONE
  delta with fully-formed arguments and the next sequential index — this is
  the parallel-complete shape and fixes the duplication;
- a marked streaming start buffers; unnamed continuation chunks append
  members; the assembled call is flushed as one delta with complete JSON on
  the text transition or terminal chunk;
- a continuation targeting an already-emitted call degrades to an
  index-addressed fragment (best-effort, keeps #7912's "no member loss"
  intent for that edge).

Request side (antigravity gemini):
- user content arriving **before any response of the pending functionCall
  group** keeps its chronological position; content arriving after a response
  still defers until the group completes (preserves #7913's grouping for
  mixed turns).

With this, all four failing tests pass, the #7912/#7913 behaviors are kept
(two of 4df055de's own tests are updated to the emit-once contract), and a
live check through the full gateway shows three parallel calls arriving as
indices `[0,1,2]`, one delta each, with complete closed arguments.

Happy to open a PR with this reconciled contract if you'd prefer it over
adjusting the two commits — the contract direction (which test family wins on
unmarked streams) is ultimately your call.

一、结论

没有发现“立即导致凭据、随机路径或 CPA 端口已直接暴露”的 P0 证据。现有防线已经明显高于普通自建代理：宿主端口 loopback-only、Nginx TLS + capability path + bearer auth、IPv6 公网监听禁止、per-IP 10r/s / 6 连接节流、429 语义、只针对真实 401/403 的 fail2ban、请求零重试、冷却不持久化、路由清单语义校验、未知目录 ID fail-closed、权限/日志保护、哈希投影与失败回滚均已落地。

但“避免单一 OAuth 账号遭受持续压力”的关键控制仍主要依赖人工纪律、客户端自律和事后观察。发现 5 项 P1 与 5 项 P2；应先实施 P1-A/B/C/D，再讨论任何阈值调整。以下建议仅用于收敛真实账户风险和服务稳定性，不涉及伪装身份、规避平台检测、账号轮换或绕过上游规则。

三、优先修复项

[P1-A] 缺少可逆、持久、可审计的 OAuth lane 隔离（quarantine）控制  【已实施，见〇节】
证据：
- scripts/remote/cpa-health.py:377-390、503-520：CPA_HEALTH_NO_OAUTH=1 仅让该次显式 health matrix 跳过 OAuth；它不阻断正常公网客户端，也不会持久化。
- README.md:128-136 明确只有客户端 semaphore 是 OAuth 聚合约束，仓库不能验证或强制。
- docs/runbooks/cpa-ban-throttle-incident-response.md:140-147 已承认静默期没有硬门。
- 官方 Management API 文档已明确提供 GET /v0/management/auth-files 与 PATCH /v0/management/auth-files/status（name/auth id + disabled），可列出并禁用/恢复单个 OAuth 凭据。
风险：疑似 312、连续 capacity、429 或 refresh 异常发生后，即使停止探针，已持有公共 key 的消费者仍可能继续请求唯一 OAuth 账号；“静默期”无法被系统强制。
修复：增加显式、可回滚的 -QuarantineOAuthLuna / -RestoreOAuthLuna 事务，而不是删除 token 或 reset quota。事务应：
1) 只读列出 auth-files，严格确认恰好一个预期 Codex OAuth 凭据；
2) 记录脱敏的前状态、时间、操作者和原因；
3) PATCH disabled=true；
4) 验证 auth-files 状态及 Luna 从可路由目录消失/被拒绝；
5) strict doctor 显示 quarantined 而非误报 OAuth 故障；
6) 恢复必须独立显式确认并 PATCH disabled=false；严禁在 L3 事件自动 POST /reset-quota。
验收：隔离后非 OAuth 模型继续 200；Luna 请求不触达 provider；恢复前不会因 timer、quality probe 或客户端重试重新启用。

[P1-B] 没有 OAuth 账号/lane 级聚合并发或速率预算  【已确认上游无此能力，见〇-补二】
证据：
- scripts/cpa_bwg_guardrails.ps1:2428-2431 / :2710-2718 的限流键为 $binary_remote_addr；它限制单 IP，不限制多个 IP 汇聚到同一个 OAuth 账号。
- README.md:120-136 直接声明 per-IP 限流不能替代账号配额，且历史全局总并发曾误伤独立 provider，已撤销。
风险：多个合法消费者、NAT 变化或泄露 key 可共同压垮唯一 OAuth 账号；每一方均未超过 per-IP 限制。
修复：不要恢复“所有 provider 共用”的全局 Nginx 限制。应在客户端路由层或专用 OAuth lane admission controller 设置只针对 Luna 的队列/并发/请求预算，其他 GLM、DeepSeek、第三方 lane 不受影响。阈值不要拍脑袋：先以 shadow-only 计数记录 OAuth 的并发、429、403、capacity、token/分钟与成功率，再根据实际 provider 条款和业务需求设置保守初值。
验收：多个不同源并发打 Luna 时，超预算请求在本地排队/失败并可观测；非 OAuth lane 的吞吐与状态码分布不发生回归。

[P1-C] 上游 Retry-After 被观测但不驱动冷却或隔离  【当前版本无可用旋钮，见〇-补二】
证据：
- scripts/cpa_bwg_guardrails.ps1:2483-2493 仅把 $upstream_http_retry_after 归类为 absent/seconds/other；:1046-1178 只做日志聚合。
- scripts/remote/cpa_policy.py:27 固定 transient-error-cooldown-seconds=60。
- docs/runbooks/cpa-ban-throttle-incident-response.md:122-133 已明确：若上游返回大于 60 秒的 Retry-After，CPA 仍可能在 60 秒后继续尝试。
风险：在 provider 明示限流窗口仍重复施压，是封号/扩大限流风险中最明确的未闭环项。
修复：先在隔离 fixture 对当前 CPA 版本做行为试验，不能假设 request-retry 或 max-retry-interval 会遵守 Retry-After。若原生不支持，则在 OAuth/provider lane admission controller 中保存“禁止到期时间”，采用 max(本地最小冷却, 合法 Retry-After)；调用端也必须尊重返回的上游头与指数退避/抖动。不要把全局 60 秒直接改大，也不要让 Nginx 全局限流替代 provider 退避。
验收：fixture 中上游返回 429 + Retry-After=600 时，到期前零次二次出站请求；其他 provider 正常；过期后仅一次低频恢复探针。

[P1-D] 未登记的未来 OAuth/Codex 模型是“事后发现”，不是请求前阻断
证据：
- scripts/remote/cpa-health.py:453-482 和 scripts/cpa_bwg_guardrails.ps1:831-876 在目录/doctor 时可发现未知 ID。
- README.md:187-191 明确写明：健康门能报错，但不能拦截直接推理请求；未来 Codex GPT-6 模型可能进入目录。
风险：新模型在下一次 doctor 之前，具有公共 key 的客户端可能直接请求它，形成未审计的账号暴露、成本、风控和质量面。
修复：优先核实当前 CPA 版本是否有真正的 request-model positive allowlist；若没有，在 CPA 前加一个小型、版本化的请求策略层，对所有可代理 OpenAI endpoint（至少 chat/completions、responses、embeddings、images）解析 JSON model 字段，仅允许由 cpa_provider_routes.json 派生的精确集合。不要用 Nginx 正则硬猜 JSON；需要可靠 JSON 解析、明确 4xx、无请求正文日志和 manifest 同步测试。
验收：未登记模型在到达 CPA 前被拒绝；登记模型正常；/models 仍 fail-closed；模型清单变更必须先提交、测试、投影再生效。

[P1-E] slot 3 仍以明文 HTTP 传输 API key 与请求内容
证据：
- scripts/remote/cpa_provider_routes.json:30-42 明确将 slot 3 标为 allow_insecure_http=true。
- README.md:170-173 承认 API key 在传输链路明文可见，并要求持续报告风险。
风险：链路上能够观察/篡改流量的一方可获得可重放 key 和非敏感之外的误投内容；这不只是“模型质量”问题，也能演变为账户滥用、异常调用和上游风控。
修复：这是架构风险，真正消除方法只有提供方 HTTPS/mTLS 或停用该 lane；当前项目约束要求不得自动移除。短期只能将其隔离为专用、低权限、可快速轮换的 key，限制该 lane 的客户端路由和敏感数据，并让上游侧按来源/IP/额度约束。此类短期措施不能等价为安全传输。
验收：在供应方 TLS 支持上线前，不把 slot 3 作为默认/敏感工作负载回退；所有调用和 key 轮换可追踪且不输出 key。

四、次优先改进

[P2-A] 健康矩阵默认仍会触碰 OAuth，开关方向应反转  【已实施，见〇节】
- cpa-health.py:503-561 在 generation-all / quality-canary / quality-eval 下默认纳入 OAuth；只有 CPA_HEALTH_NO_OAUTH=1 才排除。
- quality-eval 有 4 个 case（:50-123、:710-767），一次全矩阵会形成多次真实请求；lock 只避免并发，不限制一次运行的总消耗。
建议：OAuth 探针改为默认排除，只有 CPA_HEALTH_INCLUDE_OAUTH=1 且明确说明事件状态不是 L3 时才加入；同时设置每次执行的 probe budget、计划清单和逐 lane 延迟。保留现有 NO_OAUTH 兼容语义。

[P2-B] 降智/模型替换目前只告警，未形成确认后的自动隔离工作流
- cpa_bwg_guardrails.ps1:1320-1342 仅统计日志替换告警，超过 5 次/7d 仍只是 WARN；日志可用性依赖 CPA >= v7.3.8。
- quality-canary / quality-eval 能发现小范围语义退化，但 README.md:228-233 已正确指出其不能证明底层模型身份或长期质量。
建议：定义每个重要 lane 的“观察→人工复核→quarantine/disabled→恢复验证”状态机；至少以连续、同类、独立 case 的失败作为隔离候选，绝不因单次模型响应自动摘除。记录不可逆摘要而不是提示词/响应正文。

[P2-C] 日志审计窗口是下界，不能作为“过去 24h 全量”结论  【已由各段 coverage 覆盖，见〇-补二】
- cpa_bwg_guardrails.ps1:1065-1075 只读当前 access log 最新 64 MiB；:1173-1178 明示 rotated logs 不计入。
- :1211-1246 只检查最多 30 个、最多 7 天的保留 error dump，且转储本身由数量和 24h 保留限制。
建议：保留当前脱敏日志策略，但增加独立的聚合计数/指标快照（状态、lane、local/upstream、Retry-After 类别、OAuth quarantine 状态），并在 scan_truncated 或轮转覆盖缺失时明确标记“不可作风控窗口结论”。原始 body、Authorization、capability path 仍不得进入指标或外部系统。

[P2-D] 本地 Nginx 429 没有被验证包含明确的 Retry-After  【已实施，见〇-补二】
- cpa_bwg_guardrails.ps1:2467-2468 强制 limit_req_status/limit_conn_status 429；:2495-2503 仅记录上游 Retry-After 分类。
- strict doctor 验证状态码 :339-346，但不检查本地限流响应的 Retry-After header。
建议：仅对本地 limit_req/limit_conn 拒绝响应，使用与限流状态关联的变量产生明确、短暂的 Retry-After；不能给所有成功/上游错误响应盲目加 header。新增公网受控压测验收：429 + header、非限流 401/200/上游 5xx 的头不被伪造或覆盖。

[P2-E] 公共 key 轮换仍容易触发 fail2ban 自伤  【已改写为双 key 窗口，见〇-补二】
- cpa-fail2ban-jail.conf:7-9 为 20 次/10 分钟后封 24h；事件 runbook 已记录该已知风险。
- 当前流程主要依赖“先停止所有消费者”，多消费者环境可操作性差。
建议：确认 CPA api-keys 的多 key 语义后，设计短暂双 key 迁移：添加新 key、分消费者切换、按每客户端身份观察旧 key 使用、到期撤销旧 key。若无法做到调用方可区分，则保留现有手工流程而不是盲目缩短 bantime；另行评估 mTLS/IP 规则等第二身份因素。

五、实施顺序与安全验收

阶段 1（先做，不触碰 provider）：为 OAuth quarantine 写本地测试和 fixture，审查官方 Management API 的认证/持久化语义；定义脱敏 incident state。
阶段 2（单机、显式授权）：部署 OAuth quarantine/restore，并验证不影响非 OAuth 流量。禁止 reset-quota 自动化。
阶段 3（fixture）：验证 Retry-After=60/600、429、403、5xx、恢复窗口、未知模型拒绝和 local 429 header；所有场景应证明无多余 provider request。
阶段 4（受控 live）：先 strict doctor、单一低频 OAuth 请求或纯目录验证，再观察一整个自然窗口；确认后才开放下一项。
阶段 5（长期）：接入脱敏聚合指标与人工告警；用真实观测校准 lane 预算，而非复制全球阈值。

六、验证结果与限制

已运行：5 项定位 CPA guardrail 单测通过（OAuth 静默矩阵、policy 重试/配额 override、公开数据面契约、未知目录 ID fail-closed、Nginx 429 指令补齐）。

完整 CPA 选择集尝试结果：首个失败是 test_cpa_prune_backups_keeps_newest_backup_dirs。失败原因是当前 Windows/Git Bash 沙箱的 safe-delete shim 拒绝含盘符的临时目录删除；项目工作记忆已记录这不是脚本逻辑回归。未将此环境失败当作风险控制结论。

本报告不声称：provider 永不会限流/封号、第三方 relay 的真实模型身份、OAuth 条款允许特定自动化，或历史 2026-09-26 receipt 等同于本次在线状态。要把“风险修复”转成 live 结论，仍需在用户明确授权后遵守：先只读 doctor，再单机可回滚 Apply，最后 doctor 复验。
